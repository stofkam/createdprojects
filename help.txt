
1. Секция services: — описание контейнеров

Здесь перечисляются все сервисы (контейнеры), которые Docker должен поднять для работы проекта.

Сервис 1: db (База данных)

• image: postgres:17-alpine — скачивает готовый образ PostgreSQL 17-й версии на базе легкого Linux (Alpine), чтобы контейнер занимал меньше места.
• restart: always — автоматически перезапускает контейнер при сбоях или после перезагрузки сервера.
• environment: — задает переменные окружения внутри контейнера. Значения ${DB_USER}, ${DB_PASSWORD} и ${DB_NAME} подтягиваются из скрытого файла .env, который должен лежать рядом с docker-compose.yml:
	• POSTGRES_USER — имя пользователя БД.
	• POSTGRES_PASSWORD — пароль.
	• POSTGRES_DB — название базы, которая создастся при первом запуске.
• volumes: — подключает постоянное хранилище pgdata к внутренней папке Postgres (/var/lib/postgresql/data). Без этого все данные удалятся при перезапуске или обновлении контейнера.
• healthcheck: — проверка готовности базы к работе:
	• test — каждые 5 секунд (interval: 5s) запускает утилиту pg_isready, чтобы убедиться, что база принимает подключения. Если за 5 попыток (retries: 5) ответа нет, контейнер считается неисправным.

Сервис 2: back (Бэкенд)

• build: ./back — вместо скачивания готового образа Docker собирает его сам, используя Dockerfile, который лежит в папке ./back.
• restart: always — перезапуск при падении.
• ports: - "3000:3000" — пробрасывает порт 3000 из контейнера на порт 3000 вашего сервера (компьютера), делая API доступным извне.
• environment: — передает настройки в приложение:
	• DATABASE_URL — строка подключения к базе. Важный момент: хостом указан db (имя первого сервиса), так как внутри внутренней сети Docker контейнеры обращаются друг к другу по именам.
	• PORT: 3000 — порт, на котором запускается сам сервер бэкенда.
• depends_on: — управляет порядком запуска. Бэкенд начнет запускаться только после того, как сервис db успешно пройдет свой healthcheck (condition: service_healthy). Это защищает бэкенд от падения при попытке подключиться к еще не загрузившейся базе.

Сервис 3: front (Фронтенд)

• build: ./front — собирает образ фронтенда из папки ./front (обычно там лежит React/Vue/Angular, собранный и раздаваемый через Nginx).
• restart: always — перезапуск при сбоях.
• ports: - "80:80" — открывает стандартный HTTP-порт 80, чтобы сайт открывался в браузере просто по IP-адресу или домену без указания порта.
• depends_on: - back — фронтенд запустится только после старта контейнера back (но здесь без проверки готовности, просто по факту запуска контейнера).

2. Секция volumes: — управление данными

• pgdata: — объявляет именованный том (volume) на уровне всего Docker. Docker сам выделяет для него место на диске хоста и управляет им, сохраняя файлы базы данных в безопасности между пересборками контейнеров.

Настройка Nginx

Подготовка окружения и копирование файлов

• FROM nginx:alpine — берет легковесный официальный образ веб-сервера Nginx.
• COPY --from=builder /app/dist /usr/share/nginx/html — забирает скомпилированный фронтенд с первого этапа (builder) и кладет его в стандартную папку, откуда Nginx по умолчанию раздает сайты.

2. Перезапись конфигурации (RUN echo '...' > /etc/nginx/conf.d/default.conf)

Команда echo записывает новый текст поверх стандартного конфигурационного файла Nginx. Внутри него описан блок server:
• listen 80; — указывает Nginx принимать входящие HTTP-запросы на стандартном 80-м порту.

Блок 1: Раздача самого сайта (location /)

Отвечает за все обычные запросы пользователей (например, site.ru/ или site.ru/profile):
• root /usr/share/nginx/html; — папка, где лежат файлы сайта.
• index index.html index.htm; — главный файл, который нужно отдать при заходе в корень сайта.
• try_files $uri $uri/ /index.html; — критически важная строка для SPA (React/Vue). Если пользователь перейдет напрямую по ссылке site.ru/about, Nginx сначала поищет реальный файл или папку about. Не найдя их, он не выдаст ошибку 404 Not Found, а отдаст index.html, чтобы роутер внутри самого JavaScript-приложения отрисовал нужную страницу.

Блок 2: Проксирование запросов на бэкенд (location /api/)

Отвечает за все запросы, начинающиеся с /api/ (например, site.ru/api/users), и решает проблему CORS (так как для браузера фронтенд и бэкенд теперь находятся на одном домене и порту):
• proxy_pass http://back:3000/; — пересылает запрос внутрь сети Docker на контейнер с именем back (из вашего docker-compose.yml) на порт 3000.
	• Важный нюанс: слэш в конце http://back:3000/ обрезает префикс /api/. То есть запрос site.ru/api/users придет на бэкенд просто как /users.
• proxy_http_version 1.1; — включает протокол HTTP/1.1, необходимый для стабильного проксирования и работы WebSockets.
• Upgrade и Connection "upgrade" — заголовки, которые позволяют «обновлять» соединение (нужно, если ваше приложение использует WebSockets, например, для чатов или уведомлений).
• Host, X-Real-IP, X-Forwarded-For — служебные заголовки. Они передают бэкенду реальный IP-адрес пользователя и исходный домен, иначе бэкенд будет думать, что все запросы идут от самого контейнера Nginx.

3. Запуск сервера

• EXPOSE 80 — документирует для Docker, что контейнер использует 80-й порт.
• CMD ["nginx", "-g", "daemon off;"] — запускает Nginx на переднем плане (не в фоновом режиме). Это обязательное правило для Docker: если главный процесс уйдет в фон, контейнер решит, что работа завершена, и сразу выключится.
